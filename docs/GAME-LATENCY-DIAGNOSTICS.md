# 多開卡頓的測試與紀錄（0.1.34）

若遊戲偶爾約三秒反白、沒有回應或操作延遲，先在發生問題的電腦測試。畫面反白與網路等待可能同時出現；沒有現場紀錄時，不能把代理、遊戲、磁碟或顯示卡其中之一直接認定為根因。

## 測試方法

1. 正常關閉遊戲，再使用 0.1.34 安裝包完整更新介面與背景服務。更新會中斷代理連線；只從 ZIP 開新版介面仍可能使用舊服務。
2. 開啟已安裝的 xa sk5，在設定的技術資訊核對介面及服務版本，按「匯出診斷」保存開始前的紀錄。
3. 沿用原有兩個實例及各自線路，照原方式遊玩。發生卡頓時記下電腦時間、A/B 哪個窗口、另一個窗口是否一起停頓，以及恢復約需幾秒。不必重複測速代理。
4. 恢復後再按「匯出診斷」，保留前後兩份。若方便，同時在工作管理員記下遊戲及 WindowSocks.Service 的 CPU、記憶體、磁碟、GPU 使用情況。只有先後可對照的資料，才能區分轉送等待與遊戲本身卡住。
5. 若新版出現原本沒有的斷線，記下時間並保存診斷，正常關閉遊戲後用保留的原版本安裝包回復；不要直接覆寫執行中的服務 DLL，也不要刪除遊戲或沙盒設定。

匯出檔不含代理密碼、遊戲帳密或封包內容，但會包含程序路徑、窗口標題、節點及目的端等連線中繼資料；交付診斷時可遮蔽不需要的私人名稱。

## 新增的診斷欄位

`relayPerformance` 是服務程序啟動後的累積值，不會主動連線任何外部端點。對照兩份紀錄時，先確認同一服務程序／同一啟動階段；服務重啟會歸零。

| 欄位 | 意義 |
|---|---|
| queueSamples / queueMicroseconds | 已完成或中止之緩衝區塊的數量與累積停留微秒；不是封包數或遊戲 ping |
| queueMaxMicroseconds | 啟動後最長區塊停留時間，包含執行緒排程；歷史峰值不會自行下降 |
| wouldBlock | 非阻塞傳送當下無空間的次數；是背壓訊號，不是丟包數 |
| stallTimeouts | 任一方向有待送資料且約 5 秒沒有傳送進展，因而終止的次數 |

統計來自所有 TCP 轉送，不能單獨歸因到某個遊戲。讀取為獨立原子計數，並非同時刻的交易式快照；單一最大值不能證明最近這次卡頓的原因。關閉或長時間卡住的窗口本身也可能停止接收，使下行佇列升高。

服務原有的 `%PROGRAMDATA%\WindowSocks\diagnostics\packet-*.jsonl` 現在每秒另寫一行 `relay: true`，保存相同累積數值，維持每段約 8 MiB、最多 16 段的輪替上限。普通測試程序不會啟動持久日誌。需要逐秒比對時保留事發時段的日誌，不要公開加密設定或帳密。

## 本次修正範圍

舊核心在同一迴圈中先讀取、再用阻塞式 send_all 送完，一方向的接收端停止讀取時，另一方向也無法及時轉送。0.1.34 改用非阻塞 socket 與雙向有界緩衝；保留 TCP_NODELAY（舊版已啟用）、半關閉與既有分流安全規則。這項問題已在本機 TCP 測試重現及修正，不能代替另一台電腦的遊戲實測。
